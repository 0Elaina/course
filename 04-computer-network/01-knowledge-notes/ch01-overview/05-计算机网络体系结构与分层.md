## 体系结构设计哲学：分层与协议三要素

### 1. 为什么网络必须分层？
计算机网络要解决的课题极为繁杂（物理电平信号、相邻节点检错、跨网络动态路由、端到端进程识别、应用层业务格式等）。分层架构使得各层**高内聚、低耦合**，某一层技术的迭代（如底层升级为光纤或无线 WiFi 7）对上层业务完全透明。

- **分层的利弊权衡（课件考点）**：
  - **优点**：各层独立、灵活性好、易于实现维护、促进标准化。
  - **缺点**：有些功能会重复出现导致额外开销（如数据链路层和传输层都具备检错能力）；层数太少每一层过于复杂，层数过多描述和综合困难。
- **各层完成的 5 大共性功能**：
  1. **差错控制**：让对等端通信更可靠。
  2. **流量控制**：调节发送速率，避免撑爆接收方缓存。
  3. **分段和重装**：把大数据块拆分成合适的小段发送，在接收端还原。
  4. **复用和分用**：多个上层应用复用下层单一网络信道，接收时再准确分发。
  5. **连接建立与释放**：数据通信前先协商资源建立逻辑连接，传输后释放。

### 2. 网络协议三要素（核心考点）
- **语法（Syntax）**：数据与控制信息的结构或格式（“数据长什么样”）。
- **语义（Semantics）**：控制信息的具体含义、需发出的动作及响应（“要表达什么、做什么”）。
- **同步（Synchronization / 时序）**：事件实现顺序的详细说明（“先做什么、后做什么”）。

## 五层协议栈与数据流转过程

```
[ 发送端主机 ]                                                  [ 接收端主机 ]
  【应用层】      [ 业务报文（HTTP/JSON等） ]                          【应用层】
                         ↓                                                   ↑ 剥离 TCP 首部
  【传输层】      [ TCP首部 | 业务报文 ] (报文段 Segment)               【传输层】
                         ↓                                                   ↑ 剥离 IP 首部
  【网络层】      [ IP首部 | TCP首部 | 业务报文 ] (分组/IP数据报 Packet) 【网络层】
                         ↓                                                   ↑ 剥离 MAC 首部/尾部
【数据链路层】    [ MAC首部 | IP首部 | TCP首部 | 业务报文 | FCS尾部 ] (帧 Frame) 【数据链路层】
                         ↓                                                   ↑ 比特流还原
  【物理层】      010100101011100101... (比特流 Bit)                   【物理层】
```

### 各层协议数据单元（PDU）一览

| 层次 | 协议数据单元 (PDU) 专有名称 | 核心职责 |
| :--- | :--- | :--- |
| **应用层** | **报文（Message）** | 规定业务交互格式（HTTP、DNS、Redis 协议等）。 |
| **传输层** | **报文段（Segment）** | 提供进程间端到端可靠/不可靠传输（TCP、UDP）。 |
| **网络层** | **分组（Packet） / IP 数据报** | 主机到主机的逻辑寻址与动态路由（IP 协议）。 |
| **数据链路层** | **帧（Frame）** | 相邻节点间无差错传送（MAC 寻址与 CRC 校验）。 |
| **物理层** | **比特流（Bit Stream）** | 物理介质上的高低电平与光脉冲传输。 |

## 实体、协议、服务与 SAP 的内在联系

```
【第 N+1 层】     [ 实体 Entity (如 Tomcat 进程) ]
                        │
                  ====[ SAP (服务访问点，如端口号 8080) ]====  <-- 层间调用接口
                        │ (垂直服务 Service)
【第 N 层】       [ 实体 Entity (如 TCP 协议栈) ] <== (水平协议 Protocol) ==> [ 对等实体 ]
```

- **实体（Entity）**：任何可发送或接收信息的硬件或软件进程。
- **协议（Protocol）**：控制**两个对等实体**进行通信的规则集合（**水平方向**）。
- **服务（Service）**：下层实体向上层实体提供的功能支持（**垂直方向**）。
- **服务访问点 SAP（Service Access Point）**：相邻两层实体进行交互的门牌号（传输层的 SAP 是**端口号 Port**；网络层的 SAP 是 **IP 协议号**）。
- **SDU 与 PCI 组包公式**：
  $$\text{PDU (协议数据单元)} = \text{SDU (服务数据单元/载荷)} + \text{PCI (协议控制信息/首部)}$$

## TCP/IP 的“沙漏形状（Hourglass）”体系架构

```
         +-------------------------------------+
         | HTTP / DNS / FTP / SMTP / SSH / gRPC| (应用层丰富协议)
         +-------------------------------------+
                   \   TCP   |   UDP   /
                    \                 /
                     +---------------+
                     |   IP 协议     |  <==== 【细腰核心】：Everything over IP
                     +---------------+
                    /                 \
                   / 以太网 | WiFi | 5G \
         +-------------------------------------+
         |      各种各样的底层物理网络         | (异构物理传输网)
         +-------------------------------------+
```

- **设计精髓**：以 **IP 协议** 为唯一细腰核心枢纽。只要上层协议基于 IP（Everything over IP），下层硬件支持承载 IP（IP over Everything），就能跨越一切硬件异构性实现全球互联。

### 1. TCP/IP 体系结构的“跨层演变”（工程实践）
书本上的五层模型强调逐层封装，但工程实现中允许跨层调用：
- **跨过传输层直接访问 IP 层**：
  - 典型协议：`ping`（ICMP 协议）、OSPF 路由协议，它们不需要端口号，直接封装在 IP 数据报中传输。
  - **开发视点（原始套接字 Raw Socket）**：后端若需自研网络探测、端口扫描（如 nmap）或自定义 IP 首部，可直接创建 Raw Socket 绕过操作系统的 TCP/UDP 传输栈。
- **跨过网络层直接访问网络接口层**：
  - 典型协议：ARP（地址解析协议）直接封装在以太网帧中广播。
  - **开发视点（抓包工具）**：Wireshark、tcpdump 底层通过 libpcap 挂载在网卡驱动层，直接捕获原始二进制帧，向上透传给分析程序。

## 协议设计的极限与“两军问题”（为什么 TCP 必须三次握手？）

课件 P145 引入了计算机科学极其著名的 **两军问题（Two Generals Problem）**：
- **理论定理**：**在不可靠的物理信道上，没有任何确定性协议能达成 100% 的绝对共识。**
- **信使死循环**：发信方永远无法确信最后一封确认信是否安全送达，若追求“对方彻底确认”，就会陷入无限套娃确认。

> 💡 **后端开发与大厂面试高频必考：为什么 TCP 建立连接是三次握手？为什么不是两次或四次？**
> - **为什么不能两次？**
>   - 两次握手下，服务端回一个 ACK 就单方面建连。若客户端发出的超时旧 SYN 在网络中滞留后到达服务端，服务端会误以为是新连接而立刻打开资源等待，导致服务端**资源被僵尸连接耗尽**。
> - **为什么必须三次？**
>   - 通信是全双工的，必须验证 4 项能力：客户端（能发/能收）、服务端（能发/能收）。
>   - 第 1 次握手（Client $\to$ Server）：服务端确认“客户端能发、自己能收”。
>   - 第 2 次握手（Server $\to$ Client）：客户端确认“双方均能发能收”！（客户端闭环）。
>   - 第 3 次握手（Client $\to$ Server）：服务端确认“客户端能收、自己能发”！（服务端闭环）。
> - **为什么不是四次或更多？**
>   - 三次握手已经以**最小工程代价**达成了双方能力的完全闭环。根据“两军问题”，四次及更多次也无法杜绝最后的丢包，毫无额外工程收益。

## 避坑指南与概念辨析

1. **协议 vs 服务**：口诀牢记“**协议水平对等，服务垂直供给**”。
2. **SAP 的物理性误区**：SAP 是逻辑接口（如 `Port 8080`），并非物理插孔。
3. **OSI 七层为何失败**：非市场驱动、层次过于复杂（会话层和表示层极少独立）、效率低下；TCP/IP 是工程师在实践中自底向上构建的事实标准。
