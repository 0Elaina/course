> [!TIP]
> **30秒速记卡**
> - **`+` vs `+=`（新房 vs 扩建）**：`x = x + [1]` 触发 `__add__`，开辟全新内存，地址改变；`x += [1]` 触发 `__iadd__`，在原列表尾部原地追加（等价于 `extend`），地址不变，别名同步受影响。
> - **`*` vs `*=`**：`x * n` 生成全新重复列表；`x *= n` 原地倍增重复。
> - **嵌套乘法大坑**：`[[0] * 3] * 3` 外层乘法复制的是内层列表的**引用指针**，修改一处导致整列全变！
> - **成员运算符 `in`**：内部采用从头到尾的顺序线性扫描，时间复杂度为 $O(n)$。

## 一、运算符底层机制与内存行为矩阵

| 运算符 | 语法形式 | 底层方法 | 内存操作本质 | `id` 是否改变 | 性能表现 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **加法连接** | `a = a + b` | `__add__` | **买新房**：申请全新连续内存，拷贝两者元素 | **变** | 较慢（随着列表变大开销剧增） |
| **就地加法** | `a += b` | `__iadd__` | **旧房扩建**：直接在原列表尾部就地扩展元素 | **不变** | **极快**（推荐使用） |
| **重复乘法** | `a = a * n` | `__mul__` | **买新房**：生成包含重复元素的新列表 | **变** | 适中 |
| **就地乘法** | `a *= n` | `__imul__` | **旧房扩建**：在原列表内存中原地扩充重复项 | **不变** | 较快 |
| **成员检查** | `item in a` | `__contains__` | **逐项遍历**：从索引 0 开始线性查找直到末尾 | - | $O(n)$ 线性时间复杂度 |

## 二、核心机制图解与经典考点

### 1. 变量别名下的 `+=` 与 `+` 差异
```python
# 案例 1：+= 影响所有别名
a = [1, 2]
b = a
a += [3]
print(b)  # [1, 2, 3] -> a 和 b 指向同一地址，b 看到变化

# 案例 2：+ 创建新对象，旧别名不受影响
c = [1, 2]
d = c
c = c + [3]
print(d)  # [1, 2] -> c 搬家到了新地址，d 依然守在旧地址
```

### 2. 致命陷阱：二维矩阵的乘法浅拷贝
```python
# 错误写法：嵌套乘法
matrix = [[0] * 3] * 3
matrix[0][0] = 1
print(matrix)
# 输出不是预期的一行改变，而是全列被改：
# [[1, 0, 0], [1, 0, 0], [1, 0, 0]]
```
> **根因**：外层的 `* 3` 复制的是同一个子列表 `[0, 0, 0]` 的内存地址。三个行实际上是同一个对象！
> **正确生成矩阵姿势**：使用列表推导式（每次独立创建新列表）：
> `matrix = [[0] * 3 for _ in range(3)]`

## 三、易错避坑表

| 错误代码 / 误区 | 现象与后果 | 根因与正解 |
| :--- | :--- | :--- |
| `matrix = [[0] * 3] * 3` 修改单点 | 全列元素同步被修改 | 外层 `*` 复制了内层引用。必须改用推导式 `[[0]*3 for _ in range(3)]`。 |
| 在长列表循环中写 `res = res + [x]` | 循环随着次数增加严重卡死 | 每次 `+` 都在重新分配内存和拷贝全量历史数据，复杂度劣化为 $O(n^2)$。应改用 `res.append(x)` 或 `res += [x]`。 |
| 对元组执行 `t += [1]` 误以为在原地修改 | 若内部成功则产生迷惑，非列表报 TypeError | 元组为不可变类型，其 `+=` 本质依然会创建新元组对象。 |
